# Phase P13: Email verification at signup (6-digit code)

_Intent: see [intent.md](intent.md)._

## Objective

Registration requires proving control of the address: signup creates the account unverified, mails a single-use 6-digit code and opens no session; the auth panel switches to a code-entry state on the same surface, and the right code verifies the account and logs the reader in. Logging in with the correct password on an unverified account routes to the same code step with a 재전송 option. Existing production accounts are grandfathered as verified by the migration. No design round: the phase extends the signed R5/R12 auth vocabulary and the operator approves the exact Korean strings at the acceptance gate. The verification mail is proven live on production.

## Decisions

_Durable cross-slice decisions. Replace a superseded line; never stack versions._

**Schema — no Alembic, and NULL means verified.**

- The repo has **no Alembic and never did** (`intent.md` assumption 6 is wrong on that point; corrected here). Schema evolution is `python -m mijual.db ensure` — `create_all` for missing *tables*, then `mijual.db.schema_sync.ensure_columns` for declared-but-missing *columns*, which **raises** on any column that is `NOT NULL` or carries a `default`/`server_default`. Production runs it as the `mijual-schema` one-shot before the API starts. There is no data-migration step and none is invented.
- **`account.verification_pending_since: Mapped[datetime | None] = mapped_column(DateTime(timezone=True))`** — nullable, **no `default=`**, so `ensure_columns` accepts it. **NULL means verified.** Every existing production row therefore arrives verified with zero data work: that *is* the grandfathering, and it is a property of the column's shape, not a step anyone runs. `create_account` sets it to `utcnow()` **explicitly in the function body** (never as a column default, which `ensure_columns` would refuse); verify/reset-confirm set it back to `NULL`. It doubles as the age stamp assumption 3 asks about.
- A `verified_at`/`verified: bool` column is **rejected**: either needs a backfill this schema path cannot run.
- `Account`'s docstring names the new column **deliberately** as account *state*, not PII — the list of what must stay absent (no name, no admin flag, no conversation join, no activity trail) is unchanged.

**The code grant — `email_verification`, modelled on `PasswordReset` with three deliberate differences.**

- New table beside `password_reset`, created by `create_all` on production (so its own columns may be `NOT NULL`/defaulted — `ensure_columns` skips tables it did not find): `id`, `account_id` FK `ondelete="CASCADE"` **plus** an ORM `cascade="all, delete-orphan"` relationship on `Account` (both halves — SQLite does not enforce FKs), `code_digest String(64)`, `created_at`, `expires_at`, `used_at`, `attempts Integer NOT NULL default 0`. Index on `account_id`.
- **Difference 1 — no `UniqueConstraint` on `code_digest`, and lookup is by `account_id`, never by digest.** A reset token is 256 bits and is addressed *by itself*; a 6-digit code has 10^6 values, so two accounts can hold the same digest under the same pepper and a unique constraint would turn that collision into a 500. The code is only meaningful *with* the address.
- **Difference 2 — an `attempts` counter, and it is real (P13.F1).** `VERIFICATION_MAX_ATTEMPTS = 5`: a wrong code increments it, and a row at the cap is **not live** (same lookup predicate as expired/spent). This is assumption 2's row counter, **not** the cross-process login rate limiting still parked in P4. **The counter only bites because the failed attempt commits before the error travels.** `verify_code`'s wrong-code branch calls `db.commit()` — capturing the reached-the-cap boolean first, since the test factory expires instances on commit — and *then* raises. It is the **one place the service layer commits**, because `get_write_session` rolls back on any exception: right for every other 4xx here (a rejected 가입 leaves nothing behind) and wrong for a counter whose whole job is to make failures expensive. Between S1 and F1 the cap was **inert** (S2 measured eight wrong codes over HTTP, the row still `attempts = 0`); from F1 it is proven live over HTTP — five wrong codes answer 불일치·불일치·불일치·불일치·**만료**, the row reads `attempts = 5`, and the genuinely mailed code dies with the grant. The suite was blind to it because all three write-session fixtures committed without ever rolling back; they now mirror `get_write_session`, so the existing cap test fails on a regression (it did, before the fix — `slices/P13.F1/result.md` § 1). After the raise the dependency's `rollback()`/`close()` run on a fresh, empty transaction and are harmless.
- **Difference 3 — a resend cooldown, `VERIFICATION_RESEND_COOLDOWN = timedelta(seconds=60)`**, read from the live row's `created_at`. Without it 재전송 (and re-signup) is a mail-bomb aimed at any address. Same class of protection as the attempt counter, decided here. **As built (S1) the clock is the *most recently issued* row's `created_at`, live or not, and the cooldown outranks every caller**: nothing mails twice inside 60 seconds, not 재전송, not re-signup, not login. One service function, `issue_verification(..., force=)`, is the only thing that ever mints a code — `force=False` (login) *ensures* one exists, `force=True` (signup, 재전송) *replaces* the live one — so the throttle cannot be forgotten by a later caller.
- Otherwise the `PasswordReset` rules are copied exactly: **digest, never the secret**, through `mijual.web.auth.token_digest` (keyed with `session_pepper`, so rotating `MIJUAL_SESSION_SECRET` kills every outstanding code — a property), `expires_at`, `used_at` for single use, supersede-on-repeat (`delete` unused rows, then add). Digest comparison uses `hmac.compare_digest`.
- **`VERIFICATION_LIFETIME = timedelta(minutes=10)`** (assumption 1). The code is `f"{secrets.randbelow(1_000_000):06d}"` — uniform, **leading zeros kept**, so it is a string everywhere: the field, the payload and the mail.

**API contract — fixed here so S1 and S2 build the same thing without talking.**

- `POST /auth/signup` `{email, password}` → **201, no session, no cookie**, `{"verification": {"email": <normalized>, "expires_at": <iso>}}`. Never the code, never a token. **As built (S1): `expires_at` is *absent*, never `null`, when no live code exists** — the contract's own "absent, never null" rule. It is only reachable in one corner (the attempt cap or a spend killed the grant *and* the 60-second cooldown has not elapsed, so nothing may be re-issued yet); `email` is always present. Every route carrying a `verification` block behaves this way.
  - Address held by an **unverified** account → **re-issue, not `email_taken`** (assumption 3): the password hash **is replaced** with the one just typed (nobody has proven the mailbox, and a reader who retyped a different password must end up with the one they typed), the live code is superseded and a fresh one mailed **if** the cooldown has elapsed, otherwise the live code stands and its `expires_at` is returned. Both branches answer the identical 201 shape, so signup still discloses nothing about whether the address exists.
  - Address held by a **verified** account → `409 email_taken`, unchanged.
- `POST /auth/login` `{email, password}` — wrong password and unknown address stay one `401 invalid_credentials` at one cost (R5, `_burn_a_hash`), unchanged.
  - Correct password + **verified** → unchanged: session + cookie + `{"account": …}`.
  - Correct password + **unverified** → **no session**, `200 {"verification_required": true, "verification": {"email", "expires_at"}}`. It **issues a fresh code only when no live one exists** (honouring the cooldown otherwise), so a reader returning an hour later gets a working code without pressing 재전송 and one logging in seconds after signup gets no second mail. Disclosure is fine: it fires only after a correct password.
- `POST /auth/verify` `{email, password, code}` — **password first, then code.** Checking the password (burning a hash on a miss, exactly as `authenticate` does) means the one who verifies is the one who chose the password, which closes the pending-signup race where a second signup inside the window swaps the hash under a code the mailbox owner then enters. The panel holds both fields in state on both routes into the code step.
  - Success → `used_at` set, `verification_pending_since = NULL`, **session started + cookie set** (the `reset/confirm` precedent), `200 {"account": …}`.
  - Wrong code, grant still live → `attempts += 1`, `400 verification_code_invalid`. **Decided in S1: any wrong value costs an attempt, including one that is not six digits** (and including an empty string). A value that cannot be the code is simply not the code; exempting malformed input would add a branch whose only observable effect is a cheaper guess. The field is `code: str` with `max_length=16`, `strip()`ed, so a bad length is never a 422 — it is the ordinary structural code.
  - No live grant — expired, spent, never issued, **or killed by that same increment reaching the cap** → `400 verification_code_expired`. Two codes, not one, because the panel must point at 재전송 for the second and must not for the first.
  - Correct password on an **already verified** account → treated as a login (session + `{"account": …}`). A correct password already proves everything; inventing a failure here would only strand a reader who pressed 확인 twice.
- `POST /auth/verify/resend` `{email, password}` — password required, so it cannot be pointed at a stranger's mailbox. `200 {"resent": <bool>, "verification": {"email", "expires_at"}}`; `resent: false` when the cooldown has not elapsed (or the account is already verified) — a **state, not an error**, so the panel has one honest line for "the code we already sent is still valid" instead of a timer. Wrong password / unknown address → `401 invalid_credentials`, uniform with login. **As built (S1): on an already-verified account the block is `{"email"}` alone** (there is no code and none is coming), which is the same absent-`expires_at` rule as everywhere else.
- `POST /auth/reset/confirm` **also clears `verification_pending_since`** (assumption 4) — mailbox proven. `POST /auth/reset/request` is **unchanged** on an unverified account: 가입 여부 비노출 forbids branching the answer at all.
- `/auth/me`, `account_payload`, `/auth/logout`, `PATCH`/`DELETE /auth/account`, the chrome and `/ops` are **unchanged** (out of scope per `intent.md`).
- **Stale unverified accounts (assumption 3): no new beat entry, no sweep.** The address is never blocked — a fresh signup re-takes it at any age — which is what the assumption actually asks for. A janitor that deletes long-dead unverified rows is a **`defer-job` candidate**, listed for the review, not a slice here.

**Mail — the two-kind rule becomes three, deliberately.**

- `mijual.mail` gains `SIGNUP_VERIFICATION = "signup_verification"` (data: `code`, `expires_at`) and a third `render()` branch; `mijual.mailcopy` gains `signup_verification_subject` / `signup_verification_body`. **Both docstrings' structural rule is rewritten to say three kinds** — 마감 알림 · 비밀번호 재설정 · 가입 인증 — never slipped in (assumption 5): `mail.py`'s "Two kinds, and there will not quietly be a third" and `mailcopy.py`'s "알림 외 메일 금지. Two kinds exist".
- The mail carries the **code itself** (not a link) and its KST validity through the existing `kst_stamp`. `mailcopy.py`'s three hard rules stand: no won amount anywhere, no sentence in `data`, no second spelling of a shared label.
- **Copy route (both mail and panel): drafted in this phase, cited `drafted P13 — approved literally at the P13 gate`** — the same route `mailcopy.py` used for `drafted P4.S2`. No design round, no invented sentence outside a cited constant, and every drafted string is **listed in the acceptance walkthrough** for the operator to approve literally.
- Dev has no SMTP: `ConsoleMailer` prints the code to `var/stack/api.log`, which is how S2 reads codes in the browser. Production's `SmtpMailer` logs `smtp mailer: sent signup_verification` — the line S3 greps for.

**Frontend — one panel, a third mode.**

- **Built and swept live in S2** (the inventory below is now description, not instruction): a third `mode` inside `AuthPanel` — no verify route, no modal, no overlay — with the origin mode remembered, `email` replaced by the **normalized** address from the response, `password` kept (both calls need it), `code` reset and focused on entry. One field (`id="auth-code"`, `type="text"`, `inputMode="numeric"`, `autoComplete="one-time-code"`, `maxLength=6`, string value), 확인 → `PENDING_KO` + disabled, a quiet row of 인증번호 재전송 + the way back (labelled with the **origin mode's own name**, so it needed no constant). Client gate before any request: not exactly six digits → the drafted line, no POST (proven — the two gated submits appear nowhere in the API log). `lib/api.ts` returns `AuthResult` from both `signup` and `login`, narrowed on the **key** (`"verification" in result`), plus `verifySignup` / `resendVerification`; `Verification` lives in `lib/types.ts` with the "absent, never null" rule. **One** CSS rule was added, `.code { font-variant-numeric: tabular-nums }` — no geometry touched (panel 432/358, submit 48, field 324×48 at 390, identical to the other modes in both runtimes).
- **`SIGNUP_INTRO_KO` was false and is re-drafted** — 「… 만들어지면 바로 로그인됩니다.」 → 「… 인증번호를 메일로 보내 드립니다.」, R5's first clause untouched. It goes to the operator with the rest of the drafted strings.
- **Two live behaviours the panel is built around, both confirmed in the browser:** routing in through 로그인 **mints a code when none is live**, so the 만료 state is unreachable by logging in again (the design working — the expired line was proven by expiring a grant under the reader instead); and `resent: false` inside the cooldown mails nothing and is answered as a 알림, never an error.
- The signed R5/R12 vocabulary binds unchanged: one `p role="status"` line slot, `--alert` never on this layer, the button's own text swapped and disabled, 로그인됨 is 보유 종목 (not a panel state), and `authErrorKo` returns **`null` for any unsigned code** so the panel renders no line — the two new structural codes (`verification_code_invalid`, `verification_code_expired`) must be **mapped there or they are silently invisible**.
- `frontend/lib/api.ts`: `signup` and `login` return types become unions (`{account}` | `{verification_required, verification}`), plus `verifySignup(email, password, code)` and `resendVerification(email, password)`. `X-Mijual-CSRF` on every mutation, unchanged.

**Tests — the repo's "core behaviour only" rule.**

- The hard gate **is** core auth behaviour, so S1 updates what breaks and adds the **minimum**: signup opens no session and the right code does; login on an unverified account opens no session and routes; N wrong codes kill the code; a reset completed on an unverified account verifies it. **Nothing for the panel** — that is verified live in the browser.
- **Instrument and runtime for every browser claim: Aside on the agent account `u2`** (profile 「claude2」), `aside repl --account u2 "<js>"` — never `u0`, never `aside account use`, never `aside profile list` (hangs). Runtime is `## Operator Runtime` (`docs/current/operations.md`): `make stack-up` (API `127.0.0.1:8010`, `next dev` `:3010`), viewports **1280 and 390**, plus the **local production build** on a spare port. That section's sentence saying Aside's daemon does not run here is **stale** — P4 owes the correcting note and P12 recorded it; P13 writes no new note for it.

**Stored timestamps are naive from SQLite and aware from Postgres — read them through `_stored_utc` (P13.REVIEW closes this from S1's log).**

- `DateTime(timezone=True)` comes back **aware from Postgres** (the real target) and **naive from SQLite** (the test engine), so any *Python-side* arithmetic against `utcnow()` is a `TypeError` in the suite while working perfectly in the runtime that matters. SQL-side comparisons (`expires_at > utcnow()`) are unaffected, which is why nothing in the codebase had met this before the cooldown needed it. `mijual.web.auth._stored_utc` reads a naive stored value as UTC — the convention `mijual.web.clock.to_kst` already states — and is applied where the cooldown reads `created_at`. **Any future backend code doing Python arithmetic on a stored timestamp meets the same trap**; its docstring says so. Recorded here because S1's `result.md` called it "worth carrying" and the notebook had lost it.
