1. **There is no Alembic** (intent assumption 6 names it; the repo never had it). Schema evolution is `python -m mijual.db ensure` = `create_all` for missing tables + `mijual.db.schema_sync.ensure_columns` for declared-but-missing columns, which **refuses any column that is NOT NULL or carries a `default`/`server_default`**. Production runs it as the `mijual-schema` one-shot in `compose.prod.yml` before the API starts (`deploy/deploy.sh`). No data step exists and none should be invented.
   - **Consequence for grandfathering:** a nullable, default-free column whose **NULL means verified** is what makes every existing production row verified with zero data migration. Recommended shape: `account.verification_pending_since: DateTime(timezone=True) | None` — set to `utcnow()` explicitly in `create_account` (not as a column default), cleared to `NULL` when the code is entered or a reset completes. It also gives assumption 3 ("stale unverified accounts expire") its timestamp. A `verified_at` column would need a backfill the schema path cannot run — reject it unless you find something better, and record the choice.
   - The `Account` docstring ("email + password hash, and nothing else") must state the new column deliberately: it is account *state*, not PII, and the list of things that must stay absent is unchanged.
2. **The grant pattern to copy is `PasswordReset`** (`src/mijual/db/models.py` ~line 849; `mijual.web.auth.request_reset` / `confirm_reset`): digest-not-secret storage keyed with `session_pepper` via `token_digest`, `expires_at`, `used_at`, supersede-on-repeat (delete unused rows, then add), a uniform failure code. A new table beside it — e.g. `email_verification` (`account_id` FK `ondelete="CASCADE"` + ORM `cascade="all, delete-orphan"` on `Account`, `code_digest`, `created_at`, `expires_at`, `used_at`, and an **`attempts` counter**) is created by `create_all` on production. Lifetime ≈10 min (assumption 1); wrong attempts on one code ≈5 then the code dies (assumption 2, a row counter — not the cross-process limiter parked in P4); recommend a **resend cooldown** read from the live row's `created_at` (e.g. 60 s) so 재전송 cannot be used to mail-bomb an address — same class as the counter, decide and record it.

Two kinds exist"** and `mail.py`'s header says "Two kinds, and there will not quietly be a third"). Intent assumption 5: the rule becomes **three kinds** — deadline alert · password reset · signup verification — stated deliberately in both docstrings, with a third renderer and a `SIGNUP_VERIFICATION` kind. The new Korean mail copy is **drafted in this phase and approved literally by the operator at the gate**, cited that way in `mailcopy.py` exactly as P4.S2 cited the reset mail. Dev has no SMTP: the code prints to `var/stack/api.log` through `ConsoleMailer`, which is how the browser slice will read it.

Frontend: `frontend/components/auth/AuthPanel.tsx` (one panel, two modes, four states, one `role="status"` line slot, `--alert` never on this layer, button text swapped + disabled while 확인 중, no modal/overlay), `frontend/components/auth/copy.ts` (every Korean auth string, cited; `authErrorKo(code)` maps codes → signed lines and returns `null` for anything unsigned, so the panel renders no line), `frontend/components/auth/Auth.module.css`, `frontend/lib/api.ts` (`signup` / `login` / `requestPasswordReset` / `confirmPasswordReset`; `X-Mijual-CSRF` on every mutation). `ResetConfirmPanel.tsx` is the model for a one-field state inside the same vocabulary. Note `SIGNUP_INTRO_KO` ("… 만들어지면 바로 로그인됩니다.") becomes **false** under the gate and must be re-drafted for the operator's literal approval.
5. **Recommended API shape** (decide it here, record it in `## Decisions`, so S1 and S2 build the same contract):
   - `POST /auth/signup` → creates the account unverified, issues + mails a code, **sets no cookie**, answers `201 {"verification": {"email": <normalized>, "expires_at": …}}` (or similar — no session, no token, never the code). Signing up again with the same address while the account is unverified **re-issues** (supersedes) instead of `email_taken`; a verified account still answers `409 email_taken`. Decide whether the re-signup **replaces the password hash** (recommended: yes — nobody has proven the mailbox yet, and a reader who retyped a different password must end up with the one they typed).
   - `POST /auth/login` with the correct password on an unverified account → **no session**; answers a distinguishable success-shaped response (e.g. `200 {"verification_required": true, "verification": {...}}`) so the panel routes to the code step. Wrong password / unknown address stay one `invalid_credentials`, unchanged (R5). Decide whether that login auto-issues a fresh code when no live one exists, or leaves it to 재전송 — and record it.
   - `POST /auth/verify` (name it) — **recommended input `{email, password, code}`**, not `{email, code}`: checking the password first (burn a hash on miss, as `authenticate` does) means the one who verifies is the one who chose the password, which closes the pending-signup race where a second signup on the same address inside the window swaps the hash under a code the mailbox owner then enters; the panel holds both fields in state on both routes into the code step. On success: `verification_pending_since = NULL`, `used_at` set, **session started + cookie set** (the `reset/confirm` precedent), `{"account": …}`. Wrong code → increments `attempts`; a distinct structural code for "wrong" vs "expired / dead / none live" (the panel needs 재전송 guidance for the second), never revealing anything a correct password does not already prove.
   - `POST /auth/verify/resend` (name it) — `{email, password}` or just `{email}` — supersedes the live code, honours the cooldown, answers uniformly.
   - `POST /auth/reset/confirm` on an unverified account also clears `verification_pending_since` (assumption 4). `POST /auth/reset/request` on an unverified account: decide (recommended: send the reset mail as for any account — mailbox control is proven either way).
   - "Stale unverified accounts expire" (assumption 3): recommend **no new beat entry** — an unverified account is simply re-takeable by a fresh signup at any age, and a sweep that deletes old unverified rows is a `defer-job` candidate; record it under `## Operator Questions` only if you think the operator must choose.
   - `/auth/me`, `account_payload`, the chrome, `/ops`: unchanged (out of scope per intent).
