# Plan — P13.F1 (fix, `slice-executor-high`)

**Make the 5-attempt cap real over HTTP.** P13.S2's browser sweep proved that a wrong code's `attempts` increment never reaches the database: `mijual.web.auth.verify_code` does `grant.attempts += 1; db.flush()` and then raises `ApiError`, and `mijual.web.deps.get_write_session` rolls back on any exception (`except Exception: session.rollback(); raise`), so the increment dies with the error — 8 wrong codes over HTTP all answered `verification_code_invalid` and the row still read `attempts = 0`. A 6-digit code is therefore guessable without limit for its 10 minutes, which is exactly what `intent.md` assumption 2 forbids. The suite could not see it because `tests/test_web_auth.py`'s `_write()` override yields then commits and **never rolls back**, unlike the real dependency. ## The fix

1. **The failed attempt is the write of record, and it must be committed before the error travels.** In `verify_code`'s wrong-code branch, after `grant.attempts += 1` and the flush, **commit** the session (`db.commit()`) before raising either `ApiError` — capture `attempts` (or the "reached the cap" boolean) into a local **before** the commit, so the branch does not re-load an expired instance just to compare it. Document, in the function's docstring, that this is the one place the service layer commits and why: the dependency's rollback-on-exception is right for every other 4xx (a rejected signup must leave nothing behind), and wrong here for the same reason a failed login attempt counter anywhere must persist through the 4xx it causes. After the raise the dependency's `rollback()` + `close()` run on a fresh transaction and are harmless — say so. If you find a materially cleaner shape that keeps the service commit-free (e.g. the route answering the 400 envelope on a normal return so the dependency commits), you may take it **only** if the error envelope stays byte-identical to `errors.py`'s and no other route changes; otherwise the commit is the fix.
2. **Make the test fixtures honest.** Change `tests/test_web_auth.py`'s `_write()` override to mirror `get_write_session` — commit on normal completion, **roll back on exception**, then re-raise (no `close()`, the fixture reuses one session) — so the suite sees this class of bug. Before touching `verify_code`, run the suite once with only the fixture changed and confirm `test_five_wrong_codes_kill_the_grant_and_the_mailed_code_stops_working` **fails** (that is the regression test proving the fixture now sees what production sees); record the failing assertion in `result.md`. Apply the same rollback shape to the write-session overrides in `test_web_portfolio.py` / `test_web_ops.py` if they have the yield-then-commit form (they run signup + verify through the shared helper, so they must not silently pass on a broken increment either). Add **no** new test file; extend the existing cap test only if it does not already assert the 5th answer is `verification_code_expired` and the previously-mailed code no longer works.
3. **Check the other write paths for the same trap.** Read every `raise ApiError` in `src/mijual/web/auth.py` that follows a write in the same function (resend's cooldown path, re-signup, `confirm_reset`) and confirm each one *intends* its write to be discarded on the error; list them in `result.md` with one line each. Do not change any that are correct.
