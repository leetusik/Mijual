## Operator Questions

_Questions only the operator can answer. Append only; every entry is routed at the review — folded into the acceptance walkthrough or filed with `defer-job`. An unrouted entry is a review finding._

- **Q1 — the chrome pop-in has no remedy that is free of a signed design decision (F1).** The 로그인 link / account frame and the AI 질문 launcher both appear 27–293 ms after first paint on every desktop load, because `useAccount()` renders **nothing** until `GET /auth/me` answers and `useDesktop()` starts `false`. That "render nothing until we know" is a deliberate R5/R8 decision (`AccountSlot.tsx`: 「the slot renders nothing until the probe answers … never flashing 로그인 at a reader who is logged in」). Reserving the space is a **visible empty slot**; rendering the signed-out state first is the flash R5 rejected; a skeleton is new visual vocabulary nobody signed. Which does the operator want?
- **Q2 — the mono font swap's remedy has a cost the code already argues against (F5).** `app/fonts.ts` sets `plexMono` `preload: false` on purpose: 「mono is numerals and chips, not the body face, and it must not compete with the Korean subset for the critical font budget」. The two faces a page actually uses total **25 kB** against Noto's 284 kB. Metric-matched fallbacks (the `P4.F5` route, no network cost, needs a measured `size-adjust` per platform mono face) or preload (trivially small, but reverses a recorded decision) — or live with a ≤16.33 px reflow on a cold mobile load?
- **Q3 — should the board re-rank under a reader who is reading it (F11)?** A 60 s refresh with a moved 기준시각 replaces and re-ranks rows, and the 갱신됨 chip shifts the freshness stamp 52.55 px left. The row replacement is the product working as designed; whether it should happen while the reader is mid-page, or wait for a quiet moment / an explicit 새로고침, is a product call.
- **Q4 — the launcher's hover scale (F-note, not a defect).** `Launcher.module.css` `.launcher:hover .mark { transform: scale(1.35) }` grows the mark 32 → 43.2 px. It is composited, moves nothing else, and is the **only** hover effect in the product that changes geometry (87 controls swept across three surfaces). Keep as signed, or soften?
- **Q5 — `scrollbar-gutter` cannot be judged on this machine (F14).** `lib/scrollLock.ts` sets `body { overflow: hidden }` with no gutter compensation and there is no `scrollbar-gutter` anywhere in the CSS. On macOS overlay scrollbars the gutter measures **0** and nothing moves; on Windows / Linux / macOS "always show scroll bars" the page would widen by the scrollbar width every time a sheet opens. The one-line defensive fix (`scrollbar-gutter: stable`) is a no-op here, so it would ship **unverified**. Ship it blind, or leave it?
