## 1. What I verified myself, and where the plan was wrong

The plan asked me to re-verify rather than trust. Two results matter downstream.

**(a) The white-derivation command in the plan does not work.** The plan states
`magick in.png -trim +repage +level-colors white,white` "forces every RGB to white and leaves
alpha untouched". It does not — in ImageMagick 7.1.2-27 the default channel set includes alpha, so
the operation flattens it:

```
$ magick ~/Downloads/juju_logo_no_back.png -trim +repage +level-colors white,white out.png
$ identify out.png
out.png PNG 1213x319 8-bit Grayscale Gray 2c 547B      # 547 bytes — an all-white rectangle
$ magick out.png -alpha extract -format "%c" histogram:info:- | wc -l
1                                                       # one alpha value: fully opaque
```

Shipping that file would have put a solid white block in the nav. Two forms do work, both verified
to keep all **42** distinct alpha values while forcing every RGB to `#FFFFFF`:

```
magick in.png -trim +repage -channel RGB +level-colors white,white +channel out.png
magick in.png -trim +repage -fill white -colorize 100                out.png
```

Both produce a byte-identical 21,021 b greyscale+alpha PNG. Recorded as a `## Decisions` line; S1
owns the final choice and must state the command it actually ran.

**(b) The favicon cannot be derived — this is now evidence, not a guess.** I rendered the mark at
32px and looked at it: the Hangul is illegible mush. That closes the plan's conditional ("if the
supplied mark does not reduce legibly, that is an operator question") in the affirmative, so S2
should not spend a cycle rediscovering it. Confirmed there is no favicon of any kind today —
no `frontend/app/icon.*`, no `favicon.ico`, no `public/favicon*`.

**(c) Confirmed as stated:** trim → 1213×319; 7,488 fully-opaque pure-black px; 22,956
partial-alpha px; 356,503 transparent px carrying near-white RGB (~254,254,254 dominant, i.e. a
white-backed export knocked out) — so the black file fringes light on dark surfaces and belongs on
light ones only. `magick`/`identify` are at `/opt/homebrew/bin/`. The rendering-site table in the
plan is accurate; the `## Operator Runtime` manifest is filled with no `UNFILLED` marker.

## 2. Three findings the plan did not have

1. **The mark's Korean glyphs are half the box height.** The wordmark's ink bbox inside the trimmed
   1213×319 is **946×161 at y=158** — the sparkle cluster occupies the whole top half. So the
   Korean fills **50.5%** of the box where the retired ring's ink filled **75.7%** (ink bbox
   2096×262 of 346). `Wordmark.tsx` constrains *height*, so at R2's signed `h19`/`h17` the glyphs
   render **~9.6px / ~8.6px** tall, against the ring's 14.4px. That is below comfortable Hangul
   legibility and it is a **signed** number, so it became an operator question rather than a
   silent height bump.
2. **The ops mark's *treatment*, not just its string, breaks.** `Ops.module.css` `.mark` and
   `.doorMark` set `font-family: var(--font-mono)` (IBM Plex Mono) with `letter-spacing: 0.08em`,
   deliberately — `ops/copy.ts:31` says "an identifier, so it stays raw and mono". IBM Plex Mono
   carries no Hangul, so `주주의관제탑 운영` falls back to a system Korean face and the 0.08em
   tracking reads wrong on Hangul. Folded into the plan's `OPS_MARK` question so the operator
   answers both halves at once.
3. **Two doc lines are history and must not be swapped.** `docs/current/frontend.md:120` and
   `decisions.md:674` are supersession rows recording that the *"MIJUAL + 한글 미주알 병기"* lockup
   was superseded. Rewriting them falsifies the design record. Also `frontend.md:107`
   ("Mijual Design System") is the design project's own name — explicitly out of scope.

## 4. The cut, and what I chose against

Five slices; the rationale, the risk reasoning and the per-slice notes are in
`works/phases/active/P10/phase.md` (`## Decomposition`, `## Decisions`, `## Notes for later
slices`) — not restated here.

Two calls the plan asked me to make and justify:

- **The `RING_*` rename goes in S2, not its own slice.** The plan offered both. The constants and
  their doc comment are the *same four lines* S2 must edit anyway to change the path and the
  natural dimensions, and `Wordmark.tsx` is their only consumer — a separate slice would mean two
  slices touching four lines with a rename churn in between.
- **S3 and S4 stay separate** (the plan asked whether to merge them). They fail in opposite
  directions: S3 must not rewrite a signed sentence, S4 must not rewrite a historical one. Keeping
  them apart also means an operator question raised by S3 does not stall the doc work.

- **The empty-margin question, which `intent.md` explicitly delegated to decomposition, is
  decided: trim.** `Wordmark.tsx` passes the intrinsic `width`/`height` so the browser reserves the
  ratio box before the PNG lands; an untrimmed 2560×1440 would reserve a box ~13× too wide and
  paint the ink at a few percent of it. Natural pair: **1213×319**.
