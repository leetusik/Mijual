# R18 적용 전 검산 — 오케스트레이터

**이 파일은 디자인의 산출물이 아니다.** `handoff.md`는 읽기 전용 기록이고, 이 파일은
그것을 **적용하기 전에** 오케스트레이터가 실측으로 재현한 결과다. 두 슬라이스
(`P10.F1` · `P10.F2`)의 실행자는 이 파일을 계약이 아니라 **이미 확인된 사실**로 읽는다.

날짜: 2026-08-31 · 도구: ImageMagick (`magick`) · 대상: 적용 **전**의 워킹 트리

## 1. §① 워드마크 — 스크래치 드라이런으로 전부 재현됨

`handoff.md` §①의 명령을 그대로 스크래치 디렉터리에 실행하고(출하 파일은 건드리지 않음)
검증 표의 모든 행을 다시 쟀다. **예측과 실측이 전부 일치한다.**

| 확인 | 라운드의 예측 | 실측 | |
|---|---|---|---|
| 박스 | 1247×371 srgba | `1247x371 srgba 4.0 8 opaque=False` | ✅ |
| 비투명 픽셀 | 78,212 (무변) | **78,212** | ✅ |
| 완전 불투명 | 69,630 (무변) | **69,630** | ✅ |
| 서로 다른 알파값 | 154 (무변) | **154** | ✅ |
| 의\|관 잉크 간격 | 25px, `x=519..543` | `x=518` 잉크 있음 → `519..543` 알파 0 → `x=544` 잉크 있음 | ✅ |
| 스파클 | 222×165 at `x=1025` | `sparkle=222x165 page=+1025+0`, `1025+222=1247` | ✅ |
| 글자띠 | 1087×176 at `y=195` | `band=1087x176 page=+0+5` (crop 오프셋 190 → 절대 195) | ✅ |

**잘라내는 45열이 안전한 이유도 독립적으로 확인했다.** 명령이 제거하는 구간은
`x=530..574`이고, 알파가 이미지 **전 높이**에서 0인 구간은 `x=519..588`(70열)이다.
즉 양쪽으로 11열·14열의 여유를 두고 죽은 띠 **안쪽**만 잘린다 — 글리프에도 스파클에도
닿을 수 없다.

```
x=517 maxalpha=1          x=588 maxalpha=0
x=518 maxalpha=0.686275   x=589 maxalpha=0.596078
x=519 maxalpha=0          x=590 maxalpha=1
```

**알파 연속성 해시도 일치한다** (§①이 README의 낡은 문장을 대체하라고 지정한 그 검산):

```
소스 두 조각 이어붙인 알파 : d90e982748259b5356373cb82b5fb9fc20678947eb6df1994554b56ae895df79
후보 파생물의 알파         : d90e982748259b5356373cb82b5fb9fc20678947eb6df1994554b56ae895df79
```

파생물의 알파 채널이 소스 알파의 **순수한 이어붙이기**라는 뜻이고, 이것이 잉크 통계
3개가 변하지 않는 이유의 증명이다.

## 2. ⚠️ §①의 검증 표에 **작동하지 않는 가드가 하나** 있다

> | 불투명 근백색(「의」 카운터) | **0** | R17 함정 2의 검산, 그대로 유효 |

**`README.md`의 원문은 옳다** — 거기서는 그 검사가 **범위 한정**이다: 「the operator's first
delivery had 2,864 opaque near-white pixels **inside 「의」's ㅇ**」. 즉 **재색칠 전 소스의
카운터 영역** 안을 세는 검사다.

**R18의 표는 그 범위를 잃어버렸다.** 흰 파생물 **전체**에 대해 "불투명 AND 근백색"을 세면
재색칠 후 잉크가 전부 `#ffffff`이므로 언제나 **불투명 픽셀 수 그 자체**가 나온다:

```
magick juju2-wordmark-white.png -alpha extract -threshold 99.99% ...  →  69630
```

0이 나올 수가 없고, 따라서 **무엇이 잘못되어도 걸러내지 못한다.**

**적용 시 처리 — 이 행을 그대로 `README.md`에 옮기지 말 것.** 대신 두 가지를 쓴다:

1. **갇힌 카운터 두 섬이 그대로인지** (이쪽이 R17 함정 2의 파생물 쪽 대응물이다):

   | 섬 | 수정 전 `juju2-wordmark-white.png` | R18 후보 | |
   |---|---|---|---|
   | `50×46 at (402,226)` (「의」의 ㅇ) | 비투명 **481** | `+402+226` → **481** | ✅ |
   | `69×15 at (1014,335)` → **`(969,335)`** (「탑」의 ㅂ) | 비투명 **15** | `+969+335` → **15** | ✅ |

   (섬 좌표는 *바운딩 박스*라 테두리 픽셀이 조금 들어온다 — 그래서 값이 0이 아니라 481·15이고,
   **중요한 것은 두 값이 수정 전후로 동일하다는 것**이다.)

2. **알파 splice 해시 비교** (§1) — 알파가 소스 알파의 순수 이어붙이기임이 증명되면, 소스에서
   뚫려 있던 카운터는 정의상 파생물에서도 뚫려 있다. 이쪽이 더 강한 보증이다.

이 지적은 **처방이 아니라 검산 절차**에 대한 것이다. §①의 명령·상수·기하는 전부 옳다.

## 3. §②의 진단 — 코드에서 확인됨

- `components/chrome/Nav.module.css`: `.link { display: inline-flex; align-items: center }`,
  `.active { font-weight: 600; border-bottom-color: #fff }` — 라운드가 인용한 그대로.
- 밑줄이 이미 안정적이라는 지적도 맞다: `.link`가 `border-bottom: 2px solid transparent`로
  2px를 예약해 두었고, 파일의 기존 주석이 정확히 그렇게 말하고 있다.
- `components/chrome/Nav.tsx`는 바 링크를 `{link.label}`로 그대로 렌더한다 (`<span>` 없음,
  `data-label` 없음) — 즉 §②의 diff가 전제한 수정 전 상태와 일치한다.

## 4. §③의 진단 — 파일에서 확인됨

현재 타일 3개는 전부 알파 없는 불투명이고, 잉크 폭은 정확히 84%다:

```
icon.png        32x32   srgb  opaque=True    ink 27x20   (27/32 = 84.4%)
icon1.png       16x16   srgb  opaque=True
apple-icon.png  180x180 srgb  opaque=True    ink 151x112 (151/180 = 83.9%)
```

즉 32px 타일에서 좌우 여백이 `(32−27)/2 = 2.5px`뿐이라는 진단이 맞고, 왼쪽 성진이
테두리에 붙어 보이는 이유도 그것이다.

**대비 계산도 독립적으로 재현했다** (WCAG 상대 휘도, `#2b8e6c` → L = 0.20949):

|---|---|---|
| 흰 배경 | 4.05 | **4.046** ✅ |
| 순검정 | 5.19 | **5.19** ✅ |
